# RDP 連携の設計 — v0.2.0 と、その後の試作

更新: 2026-10-01。`design/rdp-link` の 7327192 と中断時の未コミットのレビュー反映を読み、`standard-layout.md` と統合した設計。実証結果は [調査メモ](../research/rdp-keyboard.md) に限定する。本書の P1/P2 は未実装・未検証。P0 の実装・自動検査・実機検証の区別は [検査記録](v0.2.0-checks.md) に記す。SendKeys、Raw Input の登録、低レベルフック、通常 RDP Keyboard Event の一次資料を 2026-10-01 に再確認した。API の仕様確認を試作の成功とは扱わない。

## 決定と範囲

利用者が今回選んだ範囲は **v0.2.0 の未完了作業と設計の仕上げ（P0）**。キーの書き換え、グローバルフック、独自 RDP クライアントの試作は今回動かさない。

| 段階 | 内容 | 完了条件 |
|---|---|---|
| P0 / v0.2.0 | 正確な RDP 案内、接続先 PC の標準配列の変更、RDP で見えない物理キーボードの表示 | 標準配列の設計の自動検査と実機条件を満たす |
| P1 / 次の判断 | 接続元だけで動く使い捨ての試作 | 下の方式別の関門を測定し、成功と失敗を記録する |
| P2 / 最短でも v0.3 以降 | 成功した方式を製品へ組み込む | P1 の結果と利用者の機能範囲の承認 |

**P0 の「接続先の配列」には二つの意味があったため分離する。** v0.2.0 の `SetStandard` は、MKLM が動く PC 全体の標準配列を変更する。接続元が接続先ごとに記憶する「この RDP セッションで確認した配列」という接続プロファイルは P1/P2 のためのもの。後者の設定だけを先に置いてもキーは変わらないので、P0 には追加しない。RDP セッションの配列を強制的に選べる、と表示しない。

## 確かめた事実と未確認の点

- 通常の RDP キーイベントには物理デバイス ID がない。接続先の MKLM は、そのイベントだけから接続元の JIS/US キーボードを区別できない。[Keyboard Event](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/7acaec9f-c8a6-4ee9-87d6-d9b89cf56489)
- 調査した環境では、接続元に 2 台のキーボードがあっても RDP 内は一つの配列で入力された。接続元のデバイス別レジストリ設定を接続先へ転送する機能は MKLM にない。
- 接続先が標準 JIS、接続元の報告も JIS のとき、新しい RDP セッションで JIS として入力できた。どちらの情報が表を決めたかは区別できない。接続先が標準 US の新しいセッションなど、調査メモの E7/E7b/E11 は未実施。
- **表が必ずサインイン時に決まるとは断定しない。** 入力言語（HKL）の交渉と、JIS/US の物理キー表を同一視しない。接続先の標準変更がいつ RDP の表へ反映されるかも未確認。再接続だけで直るとは案内しない。
- 接続元での `SendInput` が Windows App / mstsc を経て届くかと、接続先セッション内部での自己注入は別の実験。一方の成否を他方の証拠にしない。

前稿の「原理的に一つだけ」「リンクは情報だけしか運べない」は強すぎる。通常の RDP 経路を使う案では、接続元でデバイスを識別し、接続先の表に合うキー列を作るのが有力である。一方、独自クライアントが直接 RDP 入力を送る方式や、独自経路でデバイス情報付き入力を送る方式も設計上は存在する。後者は範囲と保守負担が大きいため見送るのであって、原理的に不可能という意味ではない。

## 方式の比較と次回の推奨

| 方式 | 得られるもの | 未解決の点 | 判断 |
|---|---|---|---|
| Windows App / mstsc の前で変換 | 普段の接続画面を使える | Raw Input と低レベルフックの対応づけ、元キーの抑止、全画面のフック順、注入の送信 | 代替候補。まず到達性 X3 を測る |
| MKLM 独自の RDP 画面 | 自分の窓でデバイスを識別し、変換後のキー列を直接送る構成を試せる | ActiveX の入力経路との二重送信、フォーカス、認証、表示、接続管理 | **P1 の第一候補**。実現可能と確定したわけではない |
| 配列情報だけを DVC で連携 | 手動プロファイルの候補を提示できる | クライアントのプラグイン対応、相手の申告と実際の表の不一致 | 変換が成功した後の P2。最初の試作には不要 |
| 独自ネットワークで打鍵を転送 | デバイス ID も送れる | 認証、配送順、再送、切断時のキー解放、セッションとデスクトップの宛先 | P0〜P2 の初期範囲から外す |
| クリップボード貼り付け | まとまった文章を転送できる | 文字入力とショートカットを代替しない。接続先 IME での未確定入力でもない | 明示的な貼り付けだけの回避策 |
| 仮想 HID キーボード | 別デバイスを作れる可能性 | ドライバーの配布と署名、RDP セッションへの配送、保守 | 現行のドライバーなし方針の範囲外 |

Microsoft の `IMsRdpClientNonScriptable::SendKeys` は、スキャンコードを含む WM_KEYDOWN の lParam 形式と key-up 配列を受ける。1 回最大 20 イベントで、その呼び出し内のキー列はまとめて送られる。単なるスキャンコード整数を `plKeyData` に入れる API ではない。独自の RDP 画面ではこの経路を試すため、外部窓向け `SendInput` の X3 を共通の必須条件にしない。[SendKeys](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpclientnonscriptable-sendkeys)

ただし ActiveX を埋め込むだけで入力を制御できるとは限らない。Raw Input の登録は同じプロセス内の同一デバイスクラスで競合しうる。親の入力窓でだけ受ける設計とコントロール側の通常入力を検証し、元キーと変換キーが両方届くなら不合格。[RegisterRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices)

低レベルフックは時間内に返す必要があり、タイムアウト時には通知なく削除されうる。Raw Input 到着待ちでフックを止めない。直前のデバイス名を次のキーの出所として扱う方式も採らない。[LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)

VHF はカーネルモードの HID ソースドライバーを使う。単に仮想キーボードを作れば RDP 内に届く、とはいえない。ただし「すべての仮想キーボードが必ずコンソールにしか届かない」とも、この調査だけでは証明できない。対象セッションへの配送を別途検証する必要がある。[Virtual HID Framework](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/virtual-hid-framework--vhf-)

## P1 の検証手順（今回は実行しない）

### A. 独自の RDP 画面（推奨）

1. 使い捨ての別プロセスに RDP コントロールを置き、対象 PC に通常の認証で接続する。資格情報を MKLM の設定やログへ保存しない。
2. 窓が前面で利用者が試験を開始した間だけ、Raw Input のデバイスを識別する。JIS/US 各 1 台のキーが同じ窓に届くことを確かめる。
3. **A1**: 自作の変換なしで、`SendKeys` の down/up が接続先へ一回ずつ届くかを確認する。通常入力が同時に送られないことも測る。
4. **A2**: Shift+2 を US では `@`、JIS では `"` として送る。Shift を同じキーボード／別キーボードで押すケースを分ける。送信先側の Shift は共有状態であるため、二つのデバイス状態を単純に混ぜない。
5. **A3**: 次の共通行列と切断処理を満たす。A1/A2 に失敗したら、その失敗を記録して実装方式を再検討する。

### B. 外部クライアント前の変換（代替）

1. **X3**: Windows App と mstsc を分け、既知のスキャンコードを接続元で注入して到達性を測る。最初はウィンドウ表示。
2. **X4**: 元キーの抑止と Raw Input による出所識別を両立できるか測る。Shift+2 のように出所だけで結果が変わるキー、二台の交互入力・同時押しを試す。
3. **X5**: 全画面、再接続、フックの登録順、フォーカス移動を測る。どれかで識別できなくなる構成は対応と表示しない。

### 共通の合格行列

- 数字・英字・記号（Shift あり／なし）、英数・半角全角・変換・無変換、Ctrl/Alt/Win ショートカット、リピート、左右修飾キー、拡張キー。
- ローマ字入力、IME オン／オフ、未確定文字、Caps Lock。文字だけでなく接続先の down/up と修飾状態をテスト用の窓で確認する。
- 二台の交互／同時入力、片方を押しながら他方を抜く、押下中の切断と再接続、Alt+Tab、全画面切替、試作の終了と異常終了。
- x64 と ARM64 を別の対応状況として記録する。ARM64 のネイティブと x64 エミュレーションを混同しない。
- パスワードや任意アプリの文章を記録しない。試験キー列と匿名デバイス名、OS/クライアント版、接続先で確認した配列、成功／失敗件数、重複・欠落、遅延だけを記録する。
- 少なくとも試験列で誤変換・重複・欠落・修飾キーの押し残しが 0。未試験項目は合格扱いにしない。有限回の成功で「どの環境でも保証」としない。

## P2 の入力とリンクの条件

押された物理キーごとに、送ったキー列と修飾状態を覚え、離したときも同じ対応を解放する。フォーカス喪失・デバイス切断・セッション切断時に送信済みの押下を解放し、未送信の列を再接続先へ持ち越さない。識別できない入力は推測で変換しない。既存フックの削除や優先権の奪い合いを復旧手段にしない。

接続先の配列は、利用者が接続先ごとに記録し、そのセッションで Shift+2 等を打って確認した値を使う。PC 名や接続先の申告だけで自動変換を開始しない。DVC は配列候補と最小限の版情報だけを運び、設定変更の命令や打鍵の転送には使わない。リンク喪失、誤った申告、古い設定、複数接続をテストする。転送ポリシーで DVC が使えなくても手動設定で成立する設計にする。

接続先の `KeyboardType Mapping`、`Layout File`、RDP キーボードの devnode、IME のレジストリ値は変更しない。標準配列を変更する場合は、利用者が通常の `SetStandard` の下見と確認を通す。

## 今日使える回避策

1. **RDP セッションで JIS と確認できた場合は、接続元の JIS キーボードを使う。** 標準 JIS に設定しただけで常に JIS になる、とまでは保証しない。
2. 接続先の Microsoft IME の設定で、Ctrl+Space に IME オン／オフを割り当てる。切り替え操作を共通化できるが、記号の JIS/US 差は解消しない。
3. 長文は接続元で入力して、許可されたクリップボード転送で利用者が貼り付ける。クリップボードを常時監視・上書きする機能は追加しない。
4. AutoHotkey の通常のホットキーは物理キーボードを区別しない。RDP 窓だけに適用しても JIS 側まで変換されるため、**二台を同時に使う解決策としては推奨しない**。US 一台に限定する一時的な試験なら候補だが、全画面を含め未検証であり、動作済みの回避策とは記載しない。

## 次回判断すること
